# Publication reliability operations

The existing press owner/kernel lock remains the only publication owner. No new Mac cron job is installed.

## Recovery and outcome records

`daily:publish:cron` now inspects exact JSON checkpoints under `tmp/cron-checkpoints` while holding that lock. Successive records for the same exact run directory collapse to one: a verified publication (`ok:true`, pushed) always wins over any later failed proof of the same run (expired `gh` auth, CDN/API outage, newer edition live), otherwise the latest update wins. Records with neither an edition identity (checkpoint or exact packaged summary) nor a push carry nothing to resume or prove (fetch/disk/discovery failures, a generation that never packaged); they stay on disk as evidence but are not candidates, so they cannot block the next day or multiply into "ambiguous". A single same-date candidate resumes through the existing full QA/provenance/staged-byte gates; a pushed candidate uses proof-only. A completed current-day publication also uses proof-only rather than buying another plate. Completed older publications do not satisfy today. Unresolved old-date or multiple identified candidate states fail closed for operator reconciliation; no evidence is automatically deleted. Explicit `--resume-candidate` / `--proof-only` remain operator recovery controls.

**Intentionally fail-closed: unresolved older candidates.** An earlier-date record that is still pending blocks every later day with "Recovery date boundary" until an operator reconciles it. This covers a record that was pushed but never proven (every same-day proof failed: CDN slow past 18 retries, expired `gh` auth), and an unpushed candidate that fails the same way on every resume (for example a persistent `qa:publish` failure). The off-host monitor reports those days as missed. Reconcile with `daily:publish:cron --proof-only <checkpoint>` (read-only, exact commit) for the pushed case, or repair and `--resume-candidate`. The cron does not automatically prove or abandon an older date, and this change does not relax the date gates.

A package written just before interruption can provide the checkpoint's missing edition identity, but only under the exact retained worktree run directory. A machine-owned atomic record in `tmp/cron-outcomes` separates `execution` from `publication` (`verified`, `other-date`, `unverified`) and explicitly leaves agent and scheduler delivery unknown. These records are not a heartbeat. Abrupt process death or a completely full disk may prevent the final outcome write; absence is not success.

Legacy pushed checkpoints can be used for proof even when publication was manually recovered in the primary repository. Uncheckpointed historical artifacts are not guessed by mtime. Do not claim automated regeneration from every pre-package failure: these require operator repair of the retained state.

## Publication date

The cron's expected date is America/New_York. `daily:process` otherwise dates edition IDs in the configured timezone (`UTC` in the active config), which disagreed from 20:00 EDT / 19:00 EST until local midnight. The cron now passes `--date <expected Eastern date>` explicitly, so the edition ID, outcome classification, recovery date boundary and monitor agree. The normal pre-07:00 schedule produced the same date either way. Manual `daily:process` without `--date` still uses the configured timezone.

## Network and disk

Each remote manifest HTTPS attempt has a 15-second wall-clock deadline that destroys the request, including hangs before headers or during the body; response size is capped at 4 MiB. Existing bounded polling preserves exact expected edition identity; permanent HTTP 4xx (except 408/429) stops polling.

Cron refresh/generation requires 5 GiB available on both repository and worktree destination. Evidence preservation additionally measures the recursive evidence bytes without following symlinks, and requires those bytes plus 5 GiB on the archive destination before making a copy. Copy failure (including ENOSPC) aborts before worktree removal; partial copies are retained, never auto-pruned. This is a preflight, not a reservation against other processes consuming space.

**Disk guard scope.** The 5 GiB generation guard applies to the cron (repository and worktree destination) and to any standalone from-scratch `daily:process --publish` (repository root, checked before the run starts). It does not apply to non-publishing `daily:process` runs, `--mode existing` remaps, `reserve:prepare` (source-only, small), or evidence preservation, which has its own measured-bytes-plus-5 GiB check.

**Intentional retention (manual limits).** Every refresh of an existing cron worktree snapshots its whole `tmp` plus changed `public/editions` paths into `tmp/retained-cron/<timestamp>-<uuid>` and pins `refs/dfe-recovery/*`, including after verified runs. Nothing prunes these automatically: the press cannot reliably tell resolved from unresolved evidence, and losing a failed plate/prompt/capture is worse than using disk. Growth is roughly one run's prompts, captures and plates per day; when headroom falls below the 5 GiB guard the cron fails closed with "Insufficient disk headroom; evidence retained" rather than deleting anything. Operators prune `tmp/retained-cron` (and the matching `refs/dfe-recovery/*`) manually after confirming the corresponding date is published and verified in `tmp/cron-outcomes`. The same applies to `<run>/prepared-reserve-attempt/` copies, `tmp/artwork-reserve-runs/` and the reserve's `consumed/` and `invalid/` sets. This is a known operational limit: without manual pruning, disk use grows until the guard stops the press.

## Off-host monitor

`.github/workflows/publication-deadline-monitor.yml` runs on GitHub independently of the Mac. Default deadline: **07:00 America/New_York**, evaluated with IANA timezone/DST rules. Scheduled checks: **11:17, 12:17, 13:17 UTC daily**; checks before the local deadline do not alert. Change repository variable `DFE_PUBLICATION_DEADLINE` (`HH:mm`) to change the local deadline; if moving it beyond the configured UTC check window, also update the schedule. GitHub can delay scheduled runs; this is not a guaranteed exact-minute alarm.

It checks the public current manifest, unique canonical live record and current Eastern date, then fetches that exact edition's `edition.json` identity. Without a machine heartbeat it reports **start state unknown**, not “cron did not start.” This proves available remote publication metadata, not playback/fidelity, served image bytes, or all QA gates. Optional `DFE_EXPECTED_EDITION_ID` lets a direct diagnostic assert a known exact ID.

Alert destination: an issue in **nock4/hermes-frontpage-engine**, title `[Frontpage publication] YYYY-MM-DD`, plus a failed GitHub Actions run. Notifications depend on the account's existing GitHub watch/Actions preferences; no Telegram/email delivery is promised. Concurrency serializes checks. Issue reconciliation lists **every** issue, open and closed, across all pages (`gh api --paginate repos/<repo>/issues?state=all`, pull requests excluded; REST listing, not search, so there is no index lag and no recency cap) and matches the exact title; exact duplicates fail closed. Per date: a miss creates the issue once, repeated misses leave the open issue alone, a miss after the issue was closed **reopens** it (a closed false alarm can no longer silence a later real miss), and a later check with full remote manifest **and** exact `edition.json` identity **closes** the real incident with a comment. Manifest-only evidence never closes it. A listed edition whose `edition.json` fetch fails is `before-deadline` (no alert) until the deadline passes, then `unavailable`. No new credentials/services: only the workflow's repository-scoped token (`contents:read`, `issues:write`).

Manual `workflow_dispatch` input `mode`:

- `diagnostic` (default): read-only real remote check plus job summary; never lists, creates or closes issues.
- `exercise-issue`: runs the same reconciliation against a clearly titled `[Frontpage publication DIAGNOSTIC] YYYY-MM-DD` issue with an injected, labelled missed result. It reconciles twice (first `created`; `reopened` on a same-day rerun; or `existing-open` when an earlier exercise crashed before closing; second must be `existing-open` with exactly one exact-title issue), then reconciles an injected healthy result (`closed`) and reads the exact issue back as `CLOSED`. It never uses the production title, so it cannot raise or resolve a real incident. The job fails if any step deviates.

Every run writes its JSON evidence to the job summary and uploads it as artifact `publication-monitor-evidence-<run id>` (90 days). The remote exercise has not been run from this change yet; it needs the pushed workflow.

## Prepared artwork reserve

A small, single-use reserve of artwork prepared ahead of the press, so a morning run does not depend on that morning's intake rotation. It never grants admission by itself.

**Automatic lifecycle:** normal eligible `daily:publish:cron` generation now invokes source-only preparation under the existing owner, after recovery discovery and clean deployed-worktree setup. Ready sets bypass intake; absent, consumed or invalidated sets are replenished. Preparation failure stops before a second fresh intake budget. Proof-only, candidate resume, explicit inspiration overrides and `DFE_ARTWORK_RESERVE=0` bypass preparation. Preparation and the subsequent mandatory fresh consumption admission have separate bounded budgets; no inspection stamp bypasses revalidation. Retained partial preparation evidence is diagnostic, not automatically trusted across invocations.

The October 20 failure exposed an operational gap: the October 18 reserve had been consumed October 19, but preparation was only an operator command. A single successful prepared set and proof-only scheduler exercise had not tested replenishment after consumption. Research fallback and optional Jev credential timeouts are not by themselves external blockers: inspect the actual hard blockers and admitted media evidence before classifying them.

- **Preparation** (source-only): `npm run reserve:prepare` (`scripts/prepare-artwork-reserve.mjs`). It runs under the existing press owner (exits `75` if a press is live) and does the following in order:
  1. Confirms the local archive ledger equals `origin/main` (manifest and every `source-bindings.json`) and is complete.
  2. Confirms **every admission module** (below) is byte-identical to `origin/main`; untracked or locally modified modules mean `blocked-undeployed-code`. `--allow-local-code` is only accepted with a separate diagnostic `--reserve-dir`, and such sets are labelled `local-diagnostic-not-deployed` / `code_matches_ref:false`, which the press refuses.
  3. Audits existing prepared sets with the production revalidation: stale sets (expired, config/code, ledger, notes, media, undeployed) move to `invalid/` with the reason and their recorded hashes untouched; a still-valid set is reported `ready` and left prepared. It is never claimed or consumed just to check, and no intake is spent.
  4. Only when no set is ready: up to four small cursor-advancing batches (12 reads and six nominations each), with aggregate limits of 48 reads, 24 nominations, 24 acquisitions and 24 inspections. Owning notes, acquired sources and exact actual-media observations accumulate across batches; already-attempted source identities are not reacquired. Ordinary selection reruns on that retained field. Six or more admitted works with verified high-confidence captures become a set; fewer is `insufficient` (exit 2), a bounded intake result—not global scarcity or proof of a provider outage. Each completed batch retains `reserve-continuation.json` with evidence and aggregate spend.
  It never composes a brief, generates a plate or publishes. Every run writes `tmp/artwork-reserve-runs/<id>/reserve-diagnostics.json`.
  - `--audit-only`: steps 1–3 only.
  - `--prove-consumption`: steps 1–3, then a proof on a **scratch copy** of the ready set. It runs the integrated normal *Mine source signals* and *Deep source autoresearch* steps (claim, revalidation, ordinary bounded admission, finalize; fresh fallback disabled), then asserts the press's finalMedia per-binding check (verified proof plus capture bytes on disk matching `capture_sha256`) and that the capture digests equal the set's. The real set stays prepared. No brief or plate.
- **Stored per set**: owning note records (path, note sha256), per work the source URL, media URL, resolved media URL, capture sha256/path and the inspector's observation (status/kind/confidence/text) as audit, `expires_at` (default 72h, max 168h), `code_matches_ref`/`code_ref`, config fingerprint and complete-ledger fingerprint. No admission stamps are reused.
- **Config fingerprint**: model, frontpage config bytes, policy versions, the explicit `HERMES_HOME` profile path, its `config.yaml` bytes and Hermes env, plus the bytes of every module transitively imported from the reserve's intake/admission entry points (`artwork-reserve`, `signal-mining`, `bookmark-intake`, `bookmark-vault-worker`, `source-research`, `creative-artifact-inspection`, `pipeline/mine-signals`, `pipeline/research-sources`). That includes selection policy, URL policy, vetted fetch, inspection transport and source inspection. `HERMES_HOME` must be set explicitly (the frontpage profile, as under the cron). There is no default-profile fallback: without it the reserve is skipped and the run uses fresh intake. Spawned non-JS helpers (Python capture tools, the Hermes binary itself) are not hashed.
- **Location**: `$DFE_ARTWORK_RESERVE_DIR`, else `~/.hermes/profiles/frontpage/cache/artwork-reserve-v1`, with `prepared/`, `claimed/`, `consumed/`, `invalid/` (+ `.reason`/`.claim`/`.consumed` sidecars). At most one prepared set exists at a time.
- **Consumption** (normal press path only: `--publish`, obsidian-allowlist, no inspiration override, not sample/manifest; disable with `DFE_ARTWORK_RESERVE=0`):
  - During *Mine source signals*, the press, verified as the existing owner, claims the newest prepared set by atomic rename and records its pid.
  - It revalidates expiry, vault root, config fingerprint, complete current ledger fingerprint, deployed-code flag, exact owning-note bytes (isolated killable worker) and freshly fetched media bytes. Any mismatch moves the set to `invalid/` with a reason.
  - A valid set replaces only that run's nomination batch; the bookmark cursor is untouched. Ordinary bounded acquisition, text research, actual-media inspection, selection, the six-window floor, editorial exclusions, finalMedia and archive gates all run as usual.
  - The set is `consumed` only if every admitted work comes from it with byte-identical fresh captures and at least **six distinct reserved works** are matched.
- **Optional infrastructure, one budget.** Any fingerprint/claim error (permissions, I/O, missing `HERMES_HOME`) is recorded and the run uses fresh intake. Finalize is called exactly once. Once the set has moved, a failed sidecar write is reported as `sidecar_error` and never triggers a second transition. A finalize exception is recorded as `finalize-error`.
- **Shared budget on fallback.** When not consumed, the attempt's files are kept in `<run>/prepared-reserve-attempt/` and the step falls back to fresh normal intake **within the same run's single 24-acquisition / 24-inspection budget**: the reserve attempt's spend is charged first, never a second 24. If the budget is exhausted, the step fails closed with the original research error (same error object) or, if research succeeded, a budget-exhausted error. `prepared-reserve-outcome.json` records the outcome, research error and budget used.
- **Fail-safe, not fail-soft.** A transient media fetch error at claim, or a transient research/API failure, retires the set to `invalid/`; it is not re-queued. One blip costs a prepared set, never safety. Re-prepare after the next intake.
- **Crash safety**: claims only happen under the single owner. A claimed set whose claimer pid is gone (or with no claim record after a minute) is retired to `invalid/` as an orphan, never re-issued. Nothing in the reserve is deleted automatically.
- **Readiness**: a set is only ready for the press when prepared from code deployed at `origin/main`. Any source edit to an admission module after preparation invalidates it with "policy/config changed since preparation". The first real set (`20261018T202302691Z-e3527a0c`) was prepared from pre-review local code and will be retired by the first audit or claim with a production reason ("policy/config changed since preparation", or "expired" after 2026-10-21T20:23Z); its file and hashes are kept.

## Remaining scope

The reserve does not change the press's schedule, owner, or gates, and adds no second monitor. New genuinely unattended generation, the remote `exercise-issue` run, and a production missed-day alert remain distinct from local tests, proof-only and read-only diagnostics.
