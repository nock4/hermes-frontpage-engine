# Daily Frontpage Engine audit, 2026-11-10

Read-only audit. Nothing was changed, restarted, deleted or published. Not committed.

## Verdict

**Rebuild the press, keep the page.** The thing you see (the React viewer, the 226-edition archive, the look of the plates) is fine and worth keeping. The thing fighting you is everything between "cron fires at 4am" and "git push": an LLM agent (Frank) running a 21-stage fail-closed pipeline under a 7,200-character prompt that tells it to never stop, never skip a gate, and fix the code itself when something breaks. Every failure gets answered with another gate, another proof format or another recovery protocol, and the newest layer is usually the next thing to break. Over the last 29 scheduled days only 11 runs were clean; 6 more published after the agent patched code mid-run, 10 needed extra runs or hands-on recovery later that day, and 2 days have no edition (Nov 7, and today so far). The pipeline itself can run clean (8 straight days, Oct 26 to Nov 2, about 27 minutes each), so this is not a broken product. It is an operating model that manufactures its own outages. Patching it again keeps that model. A small deterministic press (roughly 1,000 to 1,500 lines, 3 to 5 model calls a day, no agent in the loop) that writes the same edition format into the same viewer is the cheaper path to "a page every morning".

## What it is supposed to do

Daily at 04:00 ET, Hermes cron job `7d714808bf6f` ("Daily Frontpage Engine 4am self-healing press", profile `frontpage`, model `gpt-6.1-sol` via `openai-codex`, no fallback provider):

1. Pre-run script `daily-frontpage-self-healing-cron.sh` starts `scripts/run-daily-publish-cron.mjs`, which runs `daily:process` (21 stages).
2. Inputs: saved signals in the Obsidian vault (X bookmarks, YouTube likes, NTS likes, Chrome bookmarks).
3. Stages: mine signals, source research + browser capture, audio prep, scene brief, source contract, **image generation**, source-fidelity audit, plate inspection/artifact mapping, mapping correction, package assembly, source-image enrichment, loud source visuals, masks, interaction mesh, interpretation, enhancement plan, edition validation, **full unit suite (1,683 tests)**, production build, Playwright smoke, source-window media audit. Then `qa:publish` (npm audit twice, codebase audit, validation, unit tests, build, 25 Playwright specs / 179 cases), then (since Nov 8) an **independent visual review** in a separate Hermes session, then commit + push to `main`, GitHub "Runtime QA", live readback, "press proof" registration.
4. Publish target: `daily.nockgarden.com`, Cloudflare Pages, git-connected to `nock4/hermes-frontpage-engine` `main`. (`vercel.json` is a leftover.)
5. Delivery: a second cron (`bf977ac15457`, every 10 minutes, no agent) is the only Telegram sender.
6. Around all of it, Frank reads the script output and is told to repair code, rerun, resume, and write outcome JSON + FINAL.md.

About 8 of the 21 stages depend on a model behaving (research synthesis, vision admission of sources, brief, image generation, fidelity audit, plate mapping, mapping correction, mask planning), each fail-closed. On top sit two more model layers: the independent reviewer and Frank.

What actually ships now: 19 of the last 28 editions have exactly **one** source window. So the daily product is one bookmarked artwork, one AI-recomposed landscape plate, one clickable window back to the source.

## Root causes, ranked by pain

**1. The agent is both operator and developer, with a prompt that forbids stopping.** The cron prompt says "DAILY PRODUCTION MUST CONTINUE", "Missing automatic producer/continuation support is an in-scope code blocker to repair". So at 4am Frank writes code, gets it "independently reviewed" by another session, and pushes to `main` (12 outcome records mention a required-check bypass at push). Result: 566 commits in 7 months, 141 in October alone, 221 `fix:` vs 218 `feat:`. The repo is the agent's scratchpad.

**2. Every failure adds a gate; gates are fail-closed; the newest gate breaks next.** Timeline of layers: fidelity gate (Jul 21), press recovery (Jul 27), cron reliability / press owner / artwork reserve (Oct 18), delivery watchdog (Oct 20), per-clause transformation acceptance (Nov 6), independent review (Nov 8), review continuation (Nov 8), transport reconciliation (Nov 9). The clean streak ended Nov 3; Nov 6 and Nov 8 layers were followed by Nov 7 (fidelity block), Nov 9 and Nov 10 (review block). A missed day because a reviewer session timed out, with a QA-passing plate sitting on disk, is the design working as specified.

**3. Source admission is too strict for the supply.** 7 of 12 failures. The pipeline demanded 6 unused, pixel-verified, non-duplicate "creative" sources from a 30-day bookmark window that often has a few. This was relaxed to minimum 1 around Oct 25, which is why the late-October streak happened. `source-research.mjs` (1,572 lines) was touched by 21 commits since Oct 1, `source-selection-policy.mjs` and `source-inspection.mjs` 13 each.

**4. One provider, no fallback, for everything.** `fallback_providers: []`. Orchestrator, vision, review and (until Oct 15) images all on `openai-codex`. The current blocker is a Hermes-core idle watchdog killing the reviewer's stream after 12 seconds of silence (398 such warnings Nov 8 to 10, tiny ~9k-token context). Suspected cause: the model thinks silently longer than 12s before its first tool call in the one-shot reviewer session; I did not verify this. The response so far was PR #17, 636 lines of "exact-turn reconciliation", which by its own closeout "repairs the project adapter, not the underlying provider's 12-second SSE idle behavior".

**5. The daily path runs the whole engineering test suite.** npm audit (twice), dead-code audit, 1,683 unit tests and 179 browser cases run on every edition, some twice. None of that tests today's edition except the smoke and media audit. It makes a dependency advisory or an unrelated flaky spec a publishing outage.

**6. Two diverging copies of the code are both "live".** The cron job's workdir is the primary checkout (`main`, 11 commits behind origin, 14 modified files that agents are told to preserve as "held overlays"), while generation loads from `hermes-frontpage-engine-cron` (detached at `5ca36c8`, itself dirty with 100+ regenerated `interpretation.json` files). Fixes get "selectively activated" file by file into the primary. Nobody can say with confidence which code runs tomorrow.

**7. Environment noise.** WindowServer crash Nov 6 took the gateway down (Nov 7 ran at 08:55), a core crash Oct 29, OpenRouter balance Nov 3. A simple script would also have missed some of these, but would not have needed archaeology to recover.

## Option A: targeted repair

Goal: stop the bleeding without changing the architecture.

1. Make independent review advisory (post the verdict after publish; never block). Unsticks Nov 10 style failures. Needs your OK (cron prompt + repo change).
2. Rewrite the cron prompt: Frank may run, resume once, and report. No code edits, no pushes other than the edition commit. Code failures become a handoff. Needs your OK.
3. One clean checkout for cron pinned to `origin/main`; decide what to do with the 14 dirty files in primary (commit or drop).
4. Daily path runs only: validate today's edition, build, one smoke spec. Everything else moves to CI.
5. Freeze new gates for 30 days. Add a fallback image/vision provider (config change, your OK).
6. Drop the eight auto-approvals from the frontpage profile once step 2 lands.

Effort: about 2 to 3 focused days plus a week of watching. Run cost after: roughly today's clean-run cost (~27 min, ~1M tokens). Expected result: back to roughly the late-October level (clean most days). Downside: you still own ~22k lines of pipeline and ~6.5k lines of agent prose that neither you nor I can cheaply reason about, eight fail-closed model stages remain, and the next agent session that "hardens" something restarts the cycle.

## Option B: rebuild the press (smallest thing that ships a page daily)

Keep the viewer and archive untouched. New `press/` in the same repo, plain Node, no agent:

1. **Pick**: newest unused bookmark with a fetchable image (ledger of used URLs). Optional one vision call: "is this artwork, yes/no". On no, take the next; max 5 tries.
2. **Brief + prompt**: one model call, using the existing prompt text.
3. **Plate**: one image call. One retry, then a second provider.
4. **Map**: one vision call for hotspots. If it fails, one whole-plate hotspot.
5. **Assemble** the existing edition package, set it live in `index.json`.
6. **Check**: schema validation, `vite build`, one Playwright smoke of that edition.
7. **Ship**: commit, push, wait for Pages, screenshot.
8. **Tell**: one Telegram message with the screenshot. On failure, one line saying which step and why. No retries tomorrow, no proof registry.

Run it as a `no_agent` script cron (or launchd). Rules: fail open on taste (publish and note it), fail closed only on "page does not load". A review, if you want one, runs after publish and only leaves a note. Code changes happen in daytime sessions through PRs, never at 4am.

Size: about 1,000 to 1,500 lines plus the lifted prompts. 3 to 5 model calls per day, about 5 minutes per run. Effort: about 3 to 5 days to build and test against past sources, then a week running in shadow (build but do not publish) next to the old press, then switch the cron. Risk: relearning some edge cases the old code encodes (tweet embeds, YouTube embeddability, SSRF policy), which is why those modules are on the keep list. Needs your OK for: the new cron job, disabling the old one, and any provider/config change.

## Recommendation

**Option B**, done as a strangler: build the small press next to the old one, shadow it for a week, switch. Do Option A steps 1 and 2 right away regardless, because they stop the daily misses and the 4am commits while the rebuild happens. The evidence for B over A: the failures are not random bugs to be fixed one at a time, they come from the premise (fail-closed gates plus an agent told to add machinery until it passes), and A leaves that premise and its 22k lines in place.
